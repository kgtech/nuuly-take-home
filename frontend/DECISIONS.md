# Front-end decisions

One line of reasoning each. IDs are FE1…; service decisions (G6, G9, G11, S3) are in ../DECISIONS.md.

- [FE1] Branch name `v2-frontend`, not `v2/frontend`: git refuses `refs/heads/v2/…` while the branch `v2` exists (cannot lock ref), so the slash form is unworkable.
- [FE2] Routing: a hand-written hash router (`#/`, `#/add`, `#/sku/:skuId`) in `useHashRoute`; three routes don't justify react-router, and hashes need no server rewrite behind the Vite proxy or any static host.
- [FE3] State: React hooks only (`useState`/`useEffect`/`useRef`), one fetch per view; there is no shared client state beyond the current page, so a store would be ceremony.
- [FE4] Styling: one plain stylesheet (`styles.css`) with CSS variables, `max-width` on `main` and `flex-wrap`/`auto-fit` grids; no pixel widths, so 375px works without media queries and no UI library is pulled in.
- [FE5] API types: generated by `openapi-typescript` from `../openapi.yaml` into `src/api/schema.d.ts` (committed, regenerated by `prebuild`/`pretest`); the client derives every request and response type from `paths`/`operations`, so a contract change fails `tsc`. [OD-7] The front end calls only `/v2`, add and purchase included, and the dev proxy forwards only `/v2`, so an unversioned call cannot work by accident. Types still come from `../openapi.yaml` until the OpenAPI PR moves them to `openapi-v2.yaml`.
- [FE6] Client: `createClient(base)` returns `{ ok, status, data, next } | { ok: false, status, errorText }`; errors read the text/plain body verbatim, a network failure is `status: 0`, and no exception crosses into components.
- [FE7] Link paging: the `rel="next"` URL is parsed by a 15-line RFC 8288 parser and re-rooted onto the app's origin (path + query only), so a Link the service built for `localhost:8080` still works through the dev proxy; the proxy keeps `changeOrigin: false` for the same reason.
- [FE8] Paging controls: `limit` and `after` are sent only when the user sets them (the API's default of 250 applies otherwise); `limit` is never clamped client-side because the contract says out-of-range values are ignored or capped by the server.
- [FE9] Idempotency-Key lifecycle (`useIdempotentSubmit`): `crypto.randomUUID()` on the first submit of an action, reused while in flight and after any outcome where the server may still have applied the request (network failure or timeout = status 0, 408, 429, 5xx), dropped only after a definitive answer (2xx or another 4xx) and whenever the action's inputs (operation, skuId, quantity) change, since a different request must never reuse a key (S8); a submit while in flight is ignored and the button is disabled, so a double click sends one request. The key belongs to the stock step only: Add stock, Purchase and the Create page's initial-stock add; the details PUT sends none, since PUT is idempotent by method.
- [FE10] Validation mirrors the server (quantity integer ≥ 1 ≤ 2^31−1; skuId `^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$`) as live inline hints, and a submit is answered locally only for input the server is certain to reject; forms stay `noValidate` so nothing the server might accept is ever blocked (PROMPT.md's rule beats the issue ACs). *Amended by FE30: a local block shows a field-specific reason, never the server's text ("Invalid request"/"SKU not found"), and the button is unavailable (FE31) instead of answering a submit.*
- [FE11] Error display: every failure renders the response text unchanged in a `role="alert"` element that receives focus; successes render in `role="status"` and receive focus, so keyboard and screen-reader users learn the outcome.
- [FE12] Add-stock lives both on the SKU page (works after a 404, creating the SKU) and on `#/add` with a SKU-ID field, so a new SKU can be created without knowing a URL.
- [FE13] Testing: Vitest + jsdom + React Testing Library with an MSW in-memory server that implements the contract (ordering, Link paging, idempotency replay, error texts); MSW records non-GET requests so tests assert header reuse and request counts. The mock implements only `/v2` (FE41). Playwright (chromium only, `webServer: npm run dev`) covers the two real-service flows and is not run in CI without a service.
- [FE14] Tooling pins: TypeScript 5.x (typescript-eslint and openapi-typescript don't accept 6+/7) and ESLint 9.x (eslint-plugin-jsx-a11y has no ESLint 10 peer range yet).
- [FE15] Phone width is asserted by reading the stylesheet in a test: no `width`/`min-width` above 375px and a `max-width` present, since jsdom has no layout engine for a real 375px render.
- [FE16] Requests abort after 15 s (`AbortController`) and report as a network failure (status 0), so a hung connection re-enables the form and keeps the Idempotency-Key for the retry.
- [FE17] `limit` is sent as typed even outside 1–250 (FE8): the contract states the server ignores or caps it, so the UI shows what the API does with the value rather than a second set of rules; recorded against #36 AC 3.
- [FE18] Playwright runs both flows in two projects, desktop Chrome and a 375×667 viewport, and every interactive control has `min-height: 44px`; the stylesheet test also checks `min-width`, `grid-template-columns` and paddings for phone-hostile pixel values.
- [FE19] `uuidV4()` uses `crypto.randomUUID` when present and otherwise builds a v4 UUID from `crypto.getRandomValues`, since `randomUUID` needs a secure context and the dev server may be reached over plain http from another device.
- [FE20] An error response with an empty body renders `HTTP <status>` (e.g. a proxy 502) so the alert is never blank; a non-empty body is still shown verbatim.
- [FE21] SkuView answers an id that fails G11 locally with "SKU not found" and sends no GET, which also keeps `.` and `..` off the wire where URL normalisation would target another endpoint; same rule as FE10. *Amended by FE30: this stays for the SKU page (a typed URL, no form to correct, and 404 is what the server would say), but Find a SKU no longer shows "SKU not found"; it keeps Open unavailable with the reason under the field.*
- [FE22] Playwright runs `@axe-core/playwright` on the list, SKU and add views in both projects (zero violations), asserts `document.documentElement.scrollWidth` ≤ the viewport and saves a screenshot per view under `e2e/screenshots/` (gitignored); dark-mode buttons use `--on-accent` for ≥ 4.5:1 contrast.
- [FE23] `npm run check:api` regenerates the schema and fails on a git diff, so CI can prove the committed `schema.d.ts` matches `openapi.yaml`.
- [FE24] Dev server on 5173 and API target 8080 by default (env `VITE_PORT`, `API_URL`): these are the ports main uses (the owner asked for them, card H13), so a reviewer moves between builds without changing anything. If another project holds a port, override it by env; `scripts/gate.sh` refuses to start on a busy port. (Build v2 used 15173/18080.)
- [FE25] The Closet look comes from the owner's Claude Design file (`Inventory v2.dc.html`, https://claude.ai/design/p/eb8b8832-1477-4e2b-8188-8cce4d50a608?file=Inventory+v2.dc.html); the file could not be fetched in this session (no DesignSync tool was available), so the brief's written summary of it was the spec. Fonts are Instrument Serif and Instrument Sans from Google Fonts (a `<link>` in `index.html`, with system fallbacks so the app works offline); the seven Phosphor icons the design uses are drawn inline in `Icons.tsx` (aria-hidden, stroke on the 256 grid) instead of adding `@phosphor-icons/react`, so the bundle and the dependency list stay unchanged for seven decorative glyphs.
- [FE26] Light theme only: the design defines one palette and no dark variant, so the `prefers-color-scheme` block, `color-scheme: light dark` and `--on-accent` (which only existed to keep dark-mode buttons readable) are gone; buttons are always `#1B1A19` with white text. Contrast is kept at WCAG AA (muted `#6E6862` on `#FAF7F2` ≈ 4.6:1, error `#8E2A23` on `#F8E7E3` ≈ 6.6:1) and the axe e2e checks it in both projects. The stylesheet test now asserts there is no `prefers-color-scheme` rule.
- [FE27] Availability badges on the list (and "Rented out" beside the big number on the SKU page) use the design's threshold: quantity 0 → "Rented out" (outlined), 1–3 → "Almost gone" (error tint), above 3 → "Available" (tint); `LOW_STOCK = 3` in `InventoryList.tsx` with a unit test per boundary (0, 1, 3, 4). The list header reads "Page N · k SKUs"; quantities render with `toLocaleString()`.
- [FE28] Nothing of the design's mock mode was kept: the app always talks to the real API through the Vite proxy, and the design's local checks (`certain`, `qtyHint`, `skuHint`) already matched `certainRejection`, `quantityHint` and `skuIdHint`, so the behaviour layer (`useIdempotentSubmit`, the client, Link paging, FE9 key lifecycle, verbatim errors, `noValidate`) is untouched except that the hook's `done` state now carries the key it sent, so the success block can show the design's "Idempotency-Key {key}" line. E2E status assertions therefore use `toContainText`. *Amended by FE33: the key now sits behind a collapsed "Request reference" details element, not in the sentence.*
- [FE29] Desktop spacing (page 48px 40px 96px, cards 28px, empty state 56px 32px) lives in `:root` tokens that one `@media (max-width: 600px)` block shrinks, and the two auto-fit grids use `minmax(min(340px, 100%), 1fr)` so a 375px screen gets one column; the stylesheet test allows `max-width` (a cap), px grid tracks above 160 only inside `min(…, 100%)`, literal paddings ≤ 24px, and `min-height` ≥ 44px (the design's 46px controls). Row click opens the SKU via the link's `::after` covering the row (one link, no click handler on `<tr>`), which keeps jsx-a11y and axe clean.
- [FE30] Local blocks give a field-specific reason from `validation.ts` (`quantityReason`, `skuIdReason`, `limitReason`, and the details reasons), never the server's text: the server's sentence is generic by contract (G6) and, in an alert, looked like a server answer for a request that was never sent (ui-review items 1–3); the "certain to reject" scope of FE10 is unchanged, only the wording and the presentation.
- [FE31] One unavailable-button pattern (`SubmitButton` + `Hint` in `Messages.tsx`): `aria-disabled="true"` while a reason exists or a request is in flight, never native `disabled` (focus and the accessible name stay), the hint element always rendered with its id so `aria-describedby` always points at it, the button's `aria-describedby` listing the blocking hints, and a click or Enter on an unavailable button prevented in `onClick` (the form's `onSubmit` guards too); in flight the form is `aria-busy` and inputs are `readOnly`, so a double click sends one request without a control disappearing under the pointer.
- [FE32] The page owns the outcome area: `StockForm` reports a `StockOutcome` through `onOutcome` and renders none, `StockOutcomeView` renders the one success or failure (focused when it changes), so on the SKU page an add and a purchase can never show two disagreeing numbers; after 400 "Insufficient inventory" the page re-fetches the SKU and the "Only N on hand now. Lower the quantity or add stock." line replaces the generic 400 guidance; Purchase is unavailable with "Add stock first to create this SKU." while the page's state is 404 (a soft block, since the server would answer 404 anyway) and becomes available after an add succeeds.
- [FE33] Errors keep the server text verbatim on the first line and add one plain guidance line by status class (`writeGuidance`, writes only; reads keep their Retry button): 0/408/429/5xx → "Sending again is safe: the same request will not be applied twice." (true because FE9 reuses the key on adds, and a PUT is a full replacement), 400 → "The service refused this request. Check the values and try again.", 412 on create (`If-None-Match: *`) → "A SKU with this ID already exists. Open it to edit its details or add stock." with a link to `#/sku/:id/edit` (the server's 412 text says details changed since a read, which the Create page never did, so it stays on line 1 and our line explains it), 412 on edit → a Reload button; the Edit page's 404-on-save branch is gone because Edit always sends `If-Match`, so an absent SKU answers 412 (not 404), and the GET 404 guidance already covers a missing SKU. A create PUT that ended 0/408/429/5xx does not get the "Sending again is safe" line (the SKU may already exist): it says the SKU may or may not have been created and that sending again is fine. The Idempotency-Key moves into `<details><summary>Request reference</summary>` inside the status element so screen readers hear the sentence, not 36 hex characters.
- [FE34] Routes `#/new` (`CreateSkuPage`) and `#/sku/:id/edit` (`EditSkuPage`) join the hash router; the nav gains "New SKU". Create is two steps: (1) `PUT /v2/inventory/{skuId}/details` with `If-None-Match: *` and no key (201 navigates when initial stock is 0; 412 means the SKU exists, nothing changed); (2) for initial stock above 0, a keyed `POST /inventory/{skuId}` through `useIdempotentSubmit` with the fingerprint `add\nskuId\nquantity`, as Add stock. After step 1 succeeds the form is read-only and Retry sends only the add, never a second PUT (which would answer 412 for the SKU it just created); the key follows FE9. The SKU exists at 0 stock until the add succeeds, and the failure text says so. A network failure on the PUT resends the PUT with no key. `#/add` (add stock) stays as the way to create a SKU without details. A 412 on a later PUT after an attempt that ended 0/408/429/5xx for the same SKU ID is most likely our own lost create: the page says so, links to the SKU page (no edit link), and sends nothing else, and the user adds the stock from there. A refresh or leaving between the two steps loses the initial quantity: the SKU then exists at 0 stock with its details and the user adds stock from the SKU page. The add moves to `/v2` with the stock forms in a later PR. The lost-response message replaces the server's 412 text as its headline (an exception to showing server text verbatim, FE11/FE33) because that text says the details changed, which would be false here; it says 'most likely' because another user could have created the SKU in between, and it sends the user to the SKU page to check before adding stock (reviewer MINOR 1 and 2, PR 110).
- [FE35] The five details fields live in one `useDetailsForm` hook plus `DetailsFields` component shared by create and edit, with per-field reasons that mirror DESIGN-V2 §8 exactly (name 1–120 not blank, description ≤ 2000, amount a whole number ≥ 0 with a `^[A-Z]{3}$` currency both or neither, ≤ 10 absolute http(s) URLs ≤ 2048, initial stock 0–2,147,483,647). Images are one textarea, one URL per line (blank lines and surrounding spaces ignored): ten repeated inputs would need add/remove controls and focus management for a field most SKUs leave short, and a textarea takes a pasted list. The body always sends `description` and `images` and omits `cost` when both fields are empty, so a PUT is a faithful full replacement of what GET returned.
- [FE36] Cost is formatted with `Intl.NumberFormat(undefined, { style: 'currency', currency })` from minor units, dividing by 10^`resolvedOptions().maximumFractionDigits` so JPY (0), USD (2) and KWD (3) come out right without a table; when Intl throws on the code the page shows "<amount> <currency>" rather than nothing.
- [FE37] Edit loads `GET /v2/inventory/{id}` and sends `PUT /v2/inventory/{id}/details` with `If-Match` set to the ETag it read (never `*`; `"0"` for a SKU without details), so a concurrent edit gets 412 instead of a lost update; the client's `ApiResult` carries `etag` on its ok branch. No Idempotency-Key on PUT: a full replacement applied twice is the same state. Reload after 412 re-fetches the SKU and refills the form from the server (the user's edits are discarded on purpose: the point of 412 is to see what changed before overwriting it); 200 returns to the SKU page. A lost Edit response followed by Save with the old ETag is a 412, and Reload recovers it: a retry is safe only after Reload. The edit page also serves a SKU without details (heading "Add details").
- [FE38] The SKU page and the list read `/v2` (`getSku`, `listSkus`) so they can show details; Add stock and Purchase call the keyed `/v2` POSTs too, whose response is the whole `SkuItem` with details, so the page replaces its item with it: no v1 merge and no re-fetch after an add (the response is fresher than a GET). Only the "Insufficient inventory" re-fetch stays, under the FE47 sequence guard. Images render as `loading="lazy"` thumbnails with `alt` = the SKU name; on `error` a thumbnail is replaced by a same-size `role="img"` fallback labelled "<name> (image unavailable)". A SKU without `details` shows "No details yet" and an "Add details" link; the list shows the name or a dash.
- [FE39] The one local block for input the server might accept: a cost amount above `Number.MAX_SAFE_INTEGER` (9,007,199,254,740,991) is refused with its own reason, because a JSON number goes through a double and the page would silently send different digits than typed; the server's int64 range beyond that is unreachable from this UI, and sending a corrupted value is worse than refusing it.
- [FE40] List: an empty page after a cursor says "No SKUs after '<cursor>'." with a "Show from the start" button that clears the cursor and keeps the page size; "Per page" outside 1–250 (or non-numeric) shows "Outside 1–250. The service will use 250." while the request is sent as typed (FE17 kept); the over-cap quantity hint and the on-hand line use `toLocaleString()`; the SKU page shows the list's three badges through the same `availability`.
- [FE41] The MSW mock implements only the `/v2` contract in one in-memory store (details with a version per SKU, ETag `"<version>"` or `"0"`, `If-Match` list or `*`, `If-None-Match: *`, 412 on a failed precondition, keyed add and purchase returning `SkuItem` with replay); the unversioned handlers are gone so a v1 call fails the test. The Vite proxy forwards only `/v2` (FE5, OD-7); no service change.
- [FE42] Playwright: `details.spec.ts` covers create → edit → purchase, 409, 412 (the conflicting edit is made with `page.request.put` through the proxy with `If-Match: *`), a SKU without details, and axe + 375px on `#/new` and the edit page; `inventory.spec.ts` asserts the Request reference element, `aria-disabled` buttons with their reasons, the page-level outcome area and the guidance lines. The specs were written but not run in this session: the service on the run's `v2` tip has no v2 endpoints yet, so the orchestrator runs them once the service PR merges.
- [FE43] Image URLs are checked against what the service's `java.net.URI` path accepts (`SkuDetails.requireAbsoluteHttpUrl`: lowercase `http`/`https`, non-null host, `toASCIIString()` round-trip), not against the browser's forgiving `new URL()`: printable ASCII 0x21–0x7E without `"<>\^`{|}`, a host of letters, digits, `.` and `-`, optional userinfo and port; one reason per line ("use the URL as a browser shows it: ASCII, percent-encoded, starting with http:// or https://"), and the value is never rewritten, so a non-ASCII or spaced URL the server is certain to reject is blocked with an explanation instead of a bare 400 (review F-01). The MSW mock mirrors the same rule.
- [FE44] Text fields mirror the server's character rules: the blank check uses Java `isBlank` semantics (Unicode space separators minus the non-breaking ones plus `\t\n\v\f\r` and U+001C–U+001F; JS `trim()` would also strip NBSP and U+FEFF, which the server keeps), a name rejects any character below 0x20, 0x7F or an unpaired surrogate, a description allows `\n` and `\t` only, each with the reason "Remove control characters." (F-03). No `maxLength` on name or description: it truncates a paste silently while the reason already blocks (F-09).
- [FE45] Numeric fields (quantity, initial stock, cost amount) are read with `Number()` + `Number.isInteger` + the range, not a digits regex, because a number input reports a typed `1e3` as "1e3" and the body sends 1000, which the server accepts (F-04). A cost amount above 2^53−1 says "Amounts above 9,007,199,254,740,991 can't be entered or edited here." so a stored value that large is explained on the edit page rather than blocked without a word (F-13; FE39).
- [FE46] Focus after a control unmounts: Reload on the edit page (412) focuses the Name field once the reload resolves, and "Show from the start" on the list focuses the heading like Next page (F-07). The paging form is `aria-busy` while a page loads and Apply uses the FE31 in-flight state, but is never unavailable for an out-of-range limit (F-11, FE17). The "creates the SKU if it does not exist" note appears only for a 404 load (F-12).
- [FE47] The "Insufficient inventory" re-fetch carries an outcome sequence number: a GET that resolves after a newer outcome (an add that landed first) is dropped, so it can never overwrite a fresher quantity or message (F-08). `StockOutcomeView` holds two typed refs (status div, alert paragraph) instead of one cast ref (F-10).
- [FE48] The image-URL host is a name (`[A-Za-z0-9.-]+`) or a bracketed IPv6 literal (`\[[0-9A-Fa-f:.]+\]`), each with an optional port, because `java.net.URI` accepts `http://[::1]/a.png` and FE43's name-only class blocked it (F-fe-01); an underscore host, a space and non-ASCII stay rejected. Image lines strip only `\r`, space and tab, never `trim()`, so an NBSP or U+FEFF stays in the request exactly as shown and fails the rule with its reason (F-fe-02). The edit page answers a G11-invalid URL id with FE21's local "SKU not found" and the create link, sending nothing, as the SKU page does.
- [FE49] A number input shows text it cannot parse but reports `""` with `validity.badInput`; the optional numeric fields (initial stock, cost amount) read that flag on change and hold the reason "Enter a number." so the page never silently sends 0 or omits a cost the user is looking at (F-fe-03). The edit page keeps Save unavailable with "The service did not return a version; reload and try again." when the read carried no ETag, so FE37's If-Match is never skipped for an unconditional PUT (F-fe-04). No `maxLength` on Currency either: the reason blocks (F-fe-08).
- [FE50] Obsolete since FE38: the add response replaces the page's item, so there is no merge or re-fetch after an add. What remains is that the MSW PUT validates the body before the SKU lookup and answers 400 to an empty `If-Match`, as the service does, and the SKU page's big number uses `toLocaleString()` (F-fe-08).
- [FE51] `validity.badInput` is read on the `input` event, not `change`: React fires no change when a number input's value stays `""` (typing `e5` or pasting `1,000` into an empty field), but it always fires input (R-01); `reset` clears the flag with the values so a reloaded amount is never marked bad (R-02); the cost-pair flag (`aria-invalid`) is symmetric on amount and currency (R-06). The IPv6 host class allows a zone id (`[fe80::1%eth0]`) as `java.net.URI` does (R-03). The details error and "Retry details" button (R-04) are gone with the re-fetch (FE38). The MSW PUT answers 400 to a G11-invalid skuId and to a malformed non-empty `If-Match` (anything but `*` or a list of strong ETags), as the service does (R-05).

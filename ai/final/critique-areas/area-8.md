## Findings (differs by accident, or not recorded)

### F-8-01 [MINOR] Strong ETag on the SKU representation does not change when the quantity changes
- Location: `SkuDetailsController.withEtag` (line ~229), `GET /v2/inventory/{skuId}`, `HEAD`, and the `ETag` on `PUT .../details` 200/201.
- What is wrong: the ETag is the details version, but the 200 body includes `quantity`, which changes on every add and purchase. RFC 9110 §8.8.1 defines a strong validator as one that "changes value whenever a change occurs to the representation data that would be observable in the content of a 200 (OK) response to GET". Probed: `ETag: "0"` at quantity 50, then `ETag: "0"` at quantity 52. Any client, proxy or `If-Range`/`If-Match` logic that trusts the header sees two different bodies as one representation. The PUT response also breaks RFC 9110 §9.3.4: "An origin server MUST NOT send a validator field ... in a successful response to PUT unless the request's representation data was saved without any transformation ... and the validator field value reflects the new representation"; the PUT body is `SkuDetails`, the response is a `SkuItem` with quantity. The code comment and README record the intent ("a details validator for If-Match, not a cache key for the count"), so it is a recorded choice, but the recorded reason does not address the RFC wording; `no-store` limits caching, not the validator contract. A reviewer who knows RFC 9110 will ask why a strong ETag is on a body it does not cover.
- Evidence: `curl -si localhost:18208/v2/inventory/D1` before and after `POST /inventory/D1 {"quantity":2}`: both `ETag: "0"`, quantities 50 then 52. RFC text quoted above (https://www.rfc-editor.org/rfc/rfc9110.txt).
- Suggested fix: serve the details as their own resource (`GET .../details` with the ETag; PUT already targets it) and drop `ETag` from `SkuItem` and the PUT response, or record the deviation with the RFC sections named.

### F-8-02 [MINOR] Duplicate JSON member names are accepted, last one wins
- Location: Jackson configuration (`application.yml`, `StrictStringsConfiguration`); no duplicate detection anywhere in `src/main`.
- What is wrong: G13 and the README describe "strict JSON", but `{"quantity":1,"quantity":50}` adds 50. RFC 8259 §4: "The names within an object SHOULD be unique", and behaviour with duplicates is unpredictable across parsers, so a gateway or WAF that keeps the first value would see quantity 1 while the service writes 50. Not listed in DECISIONS or README.
- Evidence: `curl -XPOST localhost:18208/v2/inventory/D1 -H "Idempotency-Key: <uuid>" -H 'Content-Type: application/json' -d '{"quantity":1,"quantity":50}'` returns 200 `{"skuId":"D1","quantity":50}`. Jackson's default: `STRICT_DUPLICATE_DETECTION` is false (https://github.com/FasterXML/jackson-core/wiki/JsonParser-Features, via search result; UNVERIFIED for Jackson 3.x defaults beyond the observed behaviour).
- Suggested fix: enable `StreamReadFeature.STRICT_DUPLICATE_DETECTION` in the mapper customizer and map the failure to 400; add a test for both POSTs and the PUT.

### F-8-03 [MINOR] Unversioned stock reads carry no Cache-Control while /v2 reads say no-store
- Location: `GET /inventory`, `GET /inventory/{skuId}` (no `Cache-Control` in the response, probed); only `SkuDetailsController` sets it.
- What is wrong: both versions read the same live stock (parity invariant 6), yet only `/v2` tells caches not to store it. RFC 9111 §4.2.2 note: "origin servers are encouraged to send explicit directives (e.g., Cache-Control: no-cache) if they wish to prevent caching", and a 200 GET may be heuristically cached. Without Last-Modified most caches compute a zero heuristic lifetime, so real risk is low (UNVERIFIED per cache). The choice is not recorded; A27 and the code only cover /v2.
- Evidence: `curl -si localhost:18208/inventory/D1` shows no `Cache-Control`; `/v2/inventory/D1` shows `Cache-Control: no-store`.
- Suggested fix: add `Cache-Control: no-store` to the unversioned reads (no status or body change, so spec-safe) or record why not.

### F-8-04 [MINOR] Next-page Link is built from the client-supplied Host header
- Location: `Paging.link` (`ServletUriComponentsBuilder.fromCurrentContextPath()`).
- What is wrong: probed `curl -H 'Host: evil.example' 'localhost:18208/v2/inventory?limit=1'` returns `Link: <http://evil.example/v2/inventory?limit=1&after=D1>; rel="next"`. A client that follows Link blindly, or a shared cache keyed on URL, can be steered to another host. Tomcat rejects repeated Host (C1) but not a spoofed single one. The recorded scope note covers `X-Forwarded-*` only. GitHub tells clients to use Link URLs as given (https://docs.github.com/en/rest/using-the-rest-api/using-pagination-in-the-rest-api), which makes the origin of those URLs matter. Response is `no-store` on /v2, so cache poisoning is not the risk; client redirection is.
- Evidence: the curl above (output: `Link: <http://evil.example/v2/inventory?limit=1&after=D1>; rel="next"`).
- Suggested fix: emit a relative reference (RFC 8288 allows relative URI-references) or read a configured base URL; record the choice.

### F-8-05 [DECISION CHALLENGE] OD-4: rejecting `Idempotency-Key` on unversioned POSTs contradicts RFC 9110 §6.3 and the draft's silence
- Location: unversioned POST routes, OD-4, G14, README "Unversioned POSTs are not retry-safe, and they reject the key".
- What is wrong: RFC 9110 (§6.3 text) says "Other recipients SHOULD ignore unrecognized header and trailer fields"; the IETF draft (-07, expired) never tells a resource to 400 an unwanted key. The rationale (no client should believe an unversioned retry is safe) is sound and recorded, but a generic HTTP client or SDK that adds the key automatically on every POST gets 400 on a spec endpoint, and the spec's own test suite is the only client guaranteed not to. Interview question: "why is a header you do not use an error, when the RFC says ignore?" The recorded answer is "fail loudly instead of silently double-writing"; that is defensible and should be stated with the RFC sentence. Describe only; do not change.
- Evidence: `POST /inventory/L01` with `Idempotency-Key: <uuid>` returns 400 text/plain `Invalid request` (probed). RFC text at line ~1487 of rfc9110.txt.
- Suggested fix: none required; add the RFC sentence and the counter-argument to OD-4's card.

### F-8-06 [NIT] IETF draft cited without revision or status; replay not marked
- Location: DESIGN §5 ("the IETF Idempotency-Key draft ... differ"), G14 card.
- What is wrong: the draft's current text is -07 (2025-10-15), "Expired & archived" (datatracker page above); the build never says which revision it compares with, so "differs from the draft" is unfalsifiable. The draft's 422 (different payload), 409 (in-flight) and 400 (missing key) are what the table above compares. Also no `Idempotent-Replayed`-style header, so a client cannot tell a replay from a first run (Stripe has one; UNVERIFIED here, not in the fetched page).
- Evidence: draft text: "SHOULD reply with a HTTP 422", "SHOULD reply with an HTTP 409", "SHOULD reply with an HTTP 400" (draft -07 .txt).
- Suggested fix: cite `-07` and its expiry in G14; optionally add a replay header.

# Critique — std (Industry standards) — v2 @ d01852a (reviewer report; web access worked, all claims cited)

## Findings (no BLOCKER/MAJOR)
- F-std-01 MINOR — Idempotency-Key rejects the IETF draft-07 wire form (a quoted Structured-Field String, e.g. `"8e03…"`) and any non-UUID key (Stripe ≤ 255 chars; Square 1–128). Documented as `format: uuid`, so a difference, not a contradiction; but S3's reasoning covers empty keys, not the deliberate stricter format, and "Invalid request" hides bad-key vs bad-body. Record the rationale in DECISIONS-ADDED or accept optional surrounding quotes. https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-07 ; https://docs.stripe.com/api/idempotent_requests ; https://developer.squareup.com/reference/square/inventory-api/batch-change-inventory
- F-std-02 MINOR — No replay marker: Stripe sends `Idempotent-Replayed: true`; V2 collapses Executed/Replayed. Contract-neutral one-line header; add it or record why not. https://docs.stripe.com/error-low-level#idempotency
- F-std-03 MINOR — Ledger rows cannot be tied to the request (Shopify referenceDocumentUri, Square reference_id/occurred_at); a nullable idempotency_key on the ledger would answer "which rows came from key K". Operator-facing.
- F-std-04 NIT — Global key namespace with no principal (Stripe scopes per account); negligible with v4 UUIDs; one line for "scope by principal when auth arrives".

## Per-reference comparison
- Shopify: InventoryItem × Location → levels with states vs V2 one number per SKU (spec-driven). Adjust (delta) + set with compareQuantity vs V2 deltas under a row lock — same lost-update protection. Overselling: per-variant policy vs V2 DENY-only (spec). Idempotency: @idempotent UUID mandatory from 2026-04, mismatch → IDEMPOTENCY_KEY_PARAMETER_MISMATCH, replay original — V2 matches semantics, optional by G8. Pagination: Link rel="next", default 50, max 250 (opaque page_info) — V2 matches header/max; default 250 and skuId cursor on purpose (G9/C2). Audit: reason + referenceDocumentUri vs V2 reason only (F-std-03).
- Stripe: key ≤ 255 (V2 UUID, F-std-01); scope per account (F-std-04); 24h lifetime matches, but Stripe re-executes after expiry while V2 rejects with 400 forever (T1, safer, documented); mismatch → 400 matches; in-progress duplicate → Stripe 409, V2 blocks on the PK then replays (G14 rejected 409); stores all outcomes incl. 500 vs V2 not storing 500 (rollback → re-execute; better here since one transaction); replay marker (F-std-02); pagination envelope vs Link (spec constraint).
- IETF draft-07: quoted string syntax (F-std-01); UUID recommended (matches); uniqueness + fingerprint (matches: SHA-256 of parsed request); published expiry (matches); mismatch SHOULD 422 (V2 400, G14); in-progress SHOULD 409 (V2 blocks, G14); replay result (matches byte-identically).
- Square: state-machine adjustments, required idempotency_key 1–128, occurred_at out-of-order — V2 matches the append-only adjustment model and mismatch error; optional key and arrival-order on purpose. BigCommerce relative adjustments "handled one-by-one … to avoid overselling" — V2 matches exactly. commercetools optimistic versioning (409 ConcurrentModification) and offset paging — V2 uses version only for cache ordering (delta ops need no client precondition), keyset paging (G9). One commercetools sub-claim (Remove Quantity negativity) UNVERIFIED and not relied on.
- Conventions: Link per RFC 8288 with absolute URL (matches); over-max clamped silently like GitHub; text/plain fixed strings permitted by RFC 9457 §4.5 and required by the spec (D6); no X-Forwarded handling documented.

## Checked and found met
24h window published; mismatch never writes; replay byte-identical; validation failures not stored; concurrent duplicates cannot both write; key ignored on GET; no oversell in the database with per-row serialisation; append-only ledger with reason; Link/max/clamp/keyset conventions; text/plain everywhere; key format documented.

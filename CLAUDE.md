# CLAUDE.md

Rules for writing code in this repo. Each rule cites the decision in DECISIONS.md that created it. If a rule seems wrong, change the decision first.

## API contract

- [G1] Treat skuId as case-sensitive: never change its case; compare with equals().
- [G11] Validate skuId against ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$. Check it in the service with a precompiled Pattern (SkuId.isValid), never with @Pattern on the @PathVariable. The guard filter answers a ";" in the skuId segment before the controller (C3, H11). On both versions: POST add → 400 "Invalid request"; PUT /v2/inventory/{skuId}/details → 400 "Invalid request"; GET and purchase → 404 "SKU not found" without touching the database or the idempotency table (GET has no 400 in the spec). @Valid body validation runs first, so a bad body wins with 400 (G4), except where the guard filter decides (H16).
- [G11] Column: sku.sku_id varchar(64) COLLATE "C" PRIMARY KEY; inventory_ledger.sku_id references it with the same type and collation (W1).
- [G2] Stored and returned quantity is long in Java and bigint in Postgres; request quantity is Integer (V2). (refined by V2)
- [G12] Adds that would exceed 9223372036854775807 are rejected by the add's conditional UPDATE … WHERE quantity <= 9223372036854775807 - :q (E1). No row returned → 400 "Invalid request". (refined by S7, V2, W1, E1)
- [G3] On the POST operations of both versions and on PUT /v2/inventory/{skuId}/details, every client request error returns 400 text/plain, including malformed JSON, a missing body, and a wrong or missing Content-Type (instead of 415); the one exception is a failed precondition on PUT details, which is 412 (H7, H8).
- [G13] Configure Jackson to reject string→int and float→int coercion and a null quantity; ignore unknown properties (OpenAPI 3.0 allows them). An integer-valued float or exponent such as 5.0 or 1e2 is refused too: quantity is written as plain digits, with no fraction or exponent (deliberate, critique M-16; both OpenAPI quantity descriptions say so). Duplicate JSON member names are rejected on every JSON body (Jackson StreamReadFeature.STRICT_DUPLICATE_DETECTION): {"quantity":1,"quantity":2} is 400 "Invalid request" and writes nothing (critique M-11; RFC 8259 §4 says names SHOULD be unique). The same settings parse the /v2 POST bodies and the PUT /v2/inventory/{skuId}/details body.
- [G4] Use @Valid on request bodies; validation runs before the SKU lookup.
- [G5] Never delete sku rows, sku_details rows or ledger rows, and never update ledger rows: Postgres rejects UPDATE or DELETE on inventory_ledger and DELETE on sku and sku_details with P0001 (E3, A11). A SKU at 0 keeps its sku row.
- [G6] Error bodies are exactly one of: "SKU not found", "Insufficient inventory", "Invalid request", or "Internal server error" (500 only), and, on PUT /v2/inventory/{skuId}/details only, 412 with the fixed text "Details changed since you read them. Reload the SKU and retry with its new ETag." (H8). Any other error status uses its standard reason phrase (e.g. "Method Not Allowed"). Never include stock counts.
- [G7] Stock correctness is enforced by Postgres in one READ COMMITTED transaction, never by a Java-side check alone: the conditional UPDATE … WHERE quantity >= :q and CHECK (quantity >= 0) on sku.quantity are the guard, and nothing retries (E1). (refined by W1, E1)
- [G8] Unversioned POST /inventory/{skuId} and POST /inventory/{skuId}/purchase never take an Idempotency-Key: a present header, with any value (an empty value and a repeated header count), is 400 "Invalid request" and nothing is written or stored (OD-4, H3). The /v2 stock POSTs require the key (OD-3, H2).
- [G14] On /v2, write the idempotency row in the same transaction as the stock change, keyed by the key alone, storing operation, skuId and a request hash. The unversioned API never reads or writes the table (H1, H3).
- [G14] On /v2, same key + same request → replay stored status, Content-Type and body. Different operation, skuId or request → 400 "Invalid request". A key older than 24h is rejected with 400 "Invalid request" (T1); rows are never purged.
- [G9] Unversioned GET /inventory reads only `after` (last skuId) and returns a fixed page of 250 (OD-5, H4); `limit` and every other parameter are ignored. GET /v2/inventory takes optional `limit` (1–250, default 250) and `after` (H5). The page size is 250 when limit is absent or ignored, the R8 maximum (C2).
- [G9] Keyset query: WHERE sku_id > :after ORDER BY sku_id LIMIT :limit + 1 (the unversioned list's limit is the constant 250). If the extra row exists, add Link: <…>; rel="next": unversioned it carries only after (H4), /v2 carries limit and after (H5).
- [G10] No authentication.
- [G10] The spec's /inventory/** operations return only the status codes the spec lists for them (GET /inventory also answers 400 "Invalid request" for a query string that can't be decoded or repeats after, Z3; a request Tomcat rejects before routing, such as a malformed percent-escape in the path, answers 400 "Invalid request" on any operation, C1; 500 only for server faults, body "Internal server error"). The /v2/inventory/** operations return the codes listed for them in openapi-v2.yaml (200, 201, 400, 404, 412); every error is text/plain (H6, H8). Other requests under /inventory/** and /v2/inventory/** keep standard HTTP codes (404/405; GET ignores Accept, POST answers 400; see U2) with text/plain bodies. Unknown paths follow the same standard-code rule. /actuator/** and the springdoc paths (/v3/api-docs, /v3/api-docs.yaml, /v3/api-docs.yaml/**, /v3/api-docs/**, /swagger-ui.html, /swagger-ui/**) are outside this rule and keep their library behaviour (health 503 when DOWN, the Swagger UI redirect, Spring Boot's JSON error body), except that a request Tomcat rejects before routing, or a query string Tomcat can't decode, is text/plain (C1). An unknown springdoc group answers 404 with Boot's JSON error body (S6), and a direct request to /error answers 404 text/plain (C1).
- [R1] Inside the stock transaction, return an outcome value (Ok / NotFound / Insufficient / Overflow); never throw for business results. Each write returns a WriteResult of its own outcome family (add WriteResult<StockOutcome.Add>, purchase WriteResult<StockOutcome.Purchase>): Done(outcome), Stored(response) or InvalidRequest (A38). Rejections of a malformed skuId or Idempotency-Key, and of a reused key, are result values too. The controller maps every result to 200/404/400 through OutcomeResponses and StoredResponses, with no branch for another operation's outcomes (A38).
- [R1] On /v2, store 200, 404 "SKU not found", 400 "Insufficient inventory" and the overflow 400 "Invalid request" against the key; the unversioned API never stores (H3). Validation 400s are not stored.
- [R2] On /v2, claim the key with INSERT … ON CONFLICT DO NOTHING RETURNING. No row → SELECT the stored response and replay it (different operation, skuId or request hash, or a row with no stored response (A18) → 400 "Invalid request"). At READ COMMITTED a concurrent claim of the same key blocks on the primary key until the first transaction ends, then replays its response, or claims the key if the first rolled back (E1).
- [R3] Map client errors to 400 only on the POST operations of both versions and on PUT /v2/inventory/{skuId}/details; a request Tomcat rejects before routing is 400 "Invalid request" on any method (C1). Outside those operations keep Spring's 404/405 (GET ignores Accept; POST and PUT answer 400; see U2), with text/plain bodies.
- [R4] GET /inventory and GET /v2/inventory return 400 "Invalid request" only when the query string can't be decoded or repeats after (Z3). GET /inventory ignores limit in every form, so its page is always 250 (H4). On GET /v2/inventory a non-positive or non-numeric limit is ignored, so the default page of 250 applies (C2), and a limit above the max → the max (H5). after is compared as a plain string and never validated; after alone returns the next 250 rows after it, with a Link when more exist (C2).
- [R7] skuId pattern for POST add: ^[A-Za-z0-9][A-Za-z0-9._-]{0,63}$.
- [R8] The maximum and default page size is 250 on both versions; limit (1–250) exists on /v2 only (H4, H5); 250 is also the page size when limit is absent or ignored (C2).
- [R9] On /v2, keys expire after 24h: a key older than 24h is rejected with 400 (T1). No purge job.
- [S2] Never put constraint annotations on @PathVariable parameters (they switch on method validation, which answers 400).
- [S2] The service checks the skuId with SkuId.isValid() once, after a write's Idempotency-Key check (A34) and before any database or idempotency work, and returns an outcome value: add → InvalidRequest (400 "Invalid request"); PUT details → 400 "Invalid request"; purchase → NotFound and GET → empty (404 "SKU not found"). The answer is never stored. Controllers take @PathVariable String skuId, which Spring strips of ";" content; the guard filter answers a ";" in the segment first (C3).
- [S3] Idempotency-Key on the /v2 stock POSTs is required (H2); on the unversioned POSTs it must be absent, and any present value, an empty one included, is 400 (G8, H3). The controller passes the raw header to the service, which parses it with IdempotencyKey.parse before the skuId check (A34). On /v2 the key must match ^[0-9a-fA-F]{8}-([0-9a-fA-F]{4}-){3}[0-9a-fA-F]{12}$; a missing or non-matching key (an empty one included) → 400 "Invalid request", returned as an outcome value before any database work. This 400 is not stored (R1).
- [S3] Column: idempotency key uuid.
- [S5] Every error response takes its status, Content-Type and body from one helper, TextErrors, that calls .contentType(MediaType.TEXT_PLAIN): the advice and the controller return the helper's ResponseEntity, and a write's outcome goes through OutcomeResponses, which copies it into a StoredResponse, and StoredResponses, which sends that unchanged (A38); the Tomcat error valve, which can't return a ResponseEntity, takes its body from the same helper's textFor and sets text/plain itself (C1). Never rely on content negotiation for error bodies. (refined by C1, A38)
- [S5] Test each error status with Accept: application/json and assert Content-Type text/plain and the exact body.
- [S6] The advice has one @Hidden @ExceptionHandler(Exception.class): log the stack trace at ERROR and return 500 text/plain "Internal server error". If the exception is an ErrorResponse, use its status and G6's fixed text, or the status's standard reason phrase when G6 has none.
- [S6] G10 and the text/plain error contract cover /inventory/** and every other path except /actuator/** and the springdoc paths (/v3/api-docs, /v3/api-docs.yaml, /v3/api-docs.yaml/**, /v3/api-docs/**, /swagger-ui.html, /swagger-ui/**). On those library paths InventoryErrorAdvice rethrows the exception, so their errors keep library behaviour (Spring Boot's /error JSON, an empty 406, health 503 when DOWN, the Swagger UI redirect), except an undecodable query string, which gets 400 text/plain "Invalid request" on every path that reads its query, and an unknown springdoc group (/v3/api-docs/{unknown}), which answers 404 with Boot's application/json error body (the library path keeps library behaviour; InventoryErrorAdvice maps springdoc's OpenApiResourceNotFoundException to 404 and logs no ERROR), for /v3/api-docs/{unknown} and /v3/api-docs.yaml/{unknown} alike. A request Tomcat rejects before routing is text/plain on every path (C1).
- [S8] On /v2, the idempotency row's primary key is the key alone. Store operation, skuId and the request hash. On reuse, a different operation, skuId or request → 400 "Invalid request". Test the same key on another SKU and on the other /v2 POST.
- [T1] On /v2, a stored key older than 24h → 400 "Invalid request"; keys are never reused.
- [T3] When G6 has no fixed text for a status, the body is that status's standard reason phrase (HttpStatus.getReasonPhrase()), e.g. "Method Not Allowed". Keep the Allow header on 405.
- [U1] The add returns WriteResult<StockOutcome.Add>, whose outcome is Ok or Overflow (A38). Overflow → 400 "Invalid request", stored against the /v2 Idempotency-Key like NotFound and Insufficient.
- [U2] GET under /inventory/** and /v2/inventory/** ignores the Accept header (a filter sets it to application/json). POST requests and PUT /v2/…/details requests whose Accept excludes JSON, or gives it q=0 (C3), get 400 "Invalid request" (HttpMediaTypeNotAcceptableException → 400 on POST and PUT).
- [U2] Test both: GET with Accept: application/xml → 200 JSON on both versions; POST with Accept: application/xml → 400.
- [U3] Order on the unversioned POSTs: body validation (@Valid, controller) → Idempotency-Key present (any value, 400, H3) → skuId pattern (service; add 400, purchase 404) → write. Order on the /v2 POSTs: body validation (@Valid, controller) → Idempotency-Key present and well formed (service, 400) → skuId pattern (service, once; add 400, purchase 404) → claim and write, through IdempotencyStore.run (A34, H2). The guard filter decides the frozen checks before all of these (C3, H16).
- [V2] Request quantity is Integer (1 to 2,147,483,647). Stored and returned quantity is bigint in Postgres and long in Java.
- [Y3] request_hash is SHA-256 of "v2" + "\n" + operation + "\n" + skuId + "\n" + the canonical request, computed from the parsed, validated request: the quantity's decimal digits on both /v2 POSTs. A key stored by an unversioned request never matches a /v2 request (H10). Never hash the raw body.
- [Y3] Test: same key and quantity with different whitespace or an extra unknown field → replay; same key with a different quantity → 400 "Invalid request"; RequestHashTest pins the version prefix.
- [Z3] InventoryErrorAdvice maps Tomcat's InvalidParameterException (a malformed percent-escape or invalid UTF-8 in the query) to 400 "Invalid request" text/plain, ahead of the catch-all, on every path that reads its query, including /actuator/** and the springdoc paths, and logs one WARN line with the method and path and no stack trace (C1). A repeated after on GET /inventory and on GET /v2/inventory returns the same 400 (checked by inventory.web.Paging); a repeated limit is still ignored (R4).
- [Z3] The GET /inventory and GET /v2/inventory OpenAPI operations document the 400 (text/plain "Invalid request"), and the after parameter's description says it must not be repeated, in openapi.yaml and openapi-v2.yaml (H12).
- [Z3] Test the undecodable query through a real server (RANDOM_PORT, raw HTTP), since MockMvc doesn't decode the query; test a repeated after on both lists, and assert the documented 400 in ApiDocsTest for both documents.
- [C1] Tomcat's host ErrorReportValve is replaced by TextErrorReportValve, installed by a Tomcat context customizer (ServletContainerConfiguration) ordered after Spring Boot's. A request Tomcat rejects before routing (a malformed or invalid-UTF-8 percent-escape, %00 or %5C in the path, an oversized request line or header, a missing or repeated Host) gets text/plain with TextErrors.textFor(status): 400 → "Invalid request"; any other status (e.g. 505, 501) → its reason phrase. It never writes HTML, and never overwrites a body already written or an error page already rendered.
- [C1] The connector passes an encoded slash through undecoded (encodedSolidusHandling=passthrough), so /inventory/A%2FB and /v2/inventory/A%2FB reach the controller with skuId "A/B", which fails SkuId.isValid (G11): GET and purchase → 404 "SKU not found", add and PUT details → 400 "Invalid request".
- [C1] TRACE reaches Spring MVC like any other unsupported method: the connector sets allowTrace=true and the dispatcherServlet bean (ServletContainerConfiguration) is a DispatcherServlet whose doTrace only calls processRequest (never HttpServlet's echo). TRACE gets the same response as PUT: 405 text/plain "Method Not Allowed" with Spring's Allow header, or 404 on an unknown path.
- [C1] A query string Tomcat can't decode (InvalidParameterException) is answered by InventoryErrorAdvice on every path that reads its query (an unknown path or /v3/api-docs never reads one), library paths included: 400 text/plain "Invalid request" and one WARN log line (method and path, no stack trace). It is never rethrown, so Tomcat logs no ERROR for it.
- [C1] Boot's own /error endpoint is not reachable: a direct request to /error, with any method, answers 404 text/plain "Not Found", and the ErrorPage dispatch that a failed body read triggers is rendered by the same text/plain valve. Malformed chunk framing (for example a chunk size of zz) on a write route is 400 text/plain "Invalid request", never Boot's JSON or Whitelabel body (critique M-02).
- [C1] Test Tomcat rejections, the encoded slash, TRACE, library-path errors, /error (every method) and a bad chunk size on the four write routes through a real server (RANDOM_PORT, raw HTTP), since MockMvc bypasses Tomcat and the /error dispatch; assert a TRACE response never echoes request headers.
- [C2] GET /inventory always runs the keyset query with a fixed page size of 250 (R8's maximum), and GET /v2/inventory with limit when R4 accepts it, otherwise 250. The unversioned page is fixed because an unbounded list failed with OutOfMemoryError at 1M SKUs (C-02) (H4). The unversioned Link carries only after; the /v2 Link carries the page size used, e.g. limit=250, and after (H5).
- [C2] The next-page Link is built by inventory.web.Paging from the request's scheme, host, port and context path plus the routed path (/inventory or /v2/inventory), never from the raw request URI, so an encoded request path (/%69nventory) still yields a working Link. Unversioned it carries only after; /v2 carries limit and after; after is strictly encoded.
- [C2] The skuId schema, @Parameter(schema = @Schema(pattern, minLength 1, maxLength 64)) built from SkuId's constants and never @Pattern (S2), is documented on every /v2 skuId path parameter in openapi-v2.yaml only; openapi.yaml keeps the spec's plain type: string (H12). InventoryItem.quantity has minimum 0 as in the spec; GET /inventory's operation and 200 descriptions state the 250 cap and the after cursor, and GET /v2/inventory's limit parameter (default 250) documents the default page. ApiDocsTest asserts each, per document.
- [C2] Test with more than 250 SKUs: GET /inventory (no parameters, and with after alone) and GET /v2/inventory without limit return 250 and a Link, following Links visits every SKU once, and the unversioned Link never carries limit; exactly 250 SKUs gives no Link.
- [C2] The web layer's API strings live together in inventory.web.InventoryApi: the API paths (the base paths /inventory and /v2/inventory and the item, purchase and details path templates), the query parameter names and the operations' OpenAPI texts. The two springdoc groups and each document's title and version live in inventory.web.OpenApiGroups, not on a controller (H12). The controllers, JsonAcceptForGetFilter, the guard filter and inventory.web.Paging static-import them, so mapping annotations need no literal and no qualified name. Other constants stay beside the logic that owns them: SQL in StockRepository, DetailsRepository and IdempotencyStore (E2), error texts in TextErrors (G6), the skuId pattern in SkuId (G11), page sizes in InventoryService (R8, C2).
- [C3] The guard filter (InventoryRequestGuardFilter, a servlet filter that runs before handler lookup and argument resolution and classifies each request by route kind: list, item, purchase, details; H11) applies every frozen check to every route of both versions, on the routed path (decoded segments, as Spring matches, so an encoded prefix cannot bypass it). A ";" in the skuId segment, sent raw or as %3B, makes the skuId invalid: /inventory/ABC-1;lot=7 and /v2/inventory/ABC-1;lot=7 answer POST add 400 "Invalid request", PUT details 400, GET and purchase 404 "SKU not found"; nothing is written or stored, with or without an Idempotency-Key. ";" content on the literal segments (/inventory;v=1/…, …/purchase;x) is ignored, as Spring does. Controllers take @PathVariable String skuId, which Spring strips of ";" content; the filter has already decided.
- [C3] InventoryService.find checks SkuId.isValid before any database access, then runs one autocommit query with no transaction (E1), so an invalid GET skuId borrows no connection.
- [C3] On POST and PUT, the most specific Accept range compatible with application/json decides (RFC 9110): ranges are matched with isCompatibleWith, as handler lookup does, so suffix ranges such as application/*+json count; q=0 means JSON is refused. Among equally specific ranges the first listed decides (the frozen behaviour; this card once said the highest q). Spring's produces condition ignores q, so the guard filter checks it and answers 400 "Invalid request" before the controller runs (U2). application/json;q=0, "application/json;q=0, */*", */*;q=0 and "application/json;q=0, application/json;q=1" → 400; */*;q=0.1 and "application/*;q=0, application/json" → accepted. GET still ignores Accept (U2).
- [C3] Test ";" and %3B in the skuId segment and ";" on the literal segments through a real server (RANDOM_PORT, raw HTTP) and MockMvc on every mapped route with {skuId} of both versions (a route-enumeration test fails when a mapped route is unknown to the filter, H11); test the q=0 forms on both versions' POSTs and on PUT details with no sku, ledger or idempotency row written; assert find with an invalid skuId never touches the transaction manager; JsonAcceptForGetFilterTest covers /inventory;v=1/x and /%69nventory/x.
- [A18] On /v2, a committed idempotency_keys row whose status, content_type and body are NULL answers 400 "Invalid request" (IdempotencyStore.Keyed.Invalid), whatever its age: it is never replayed, the write never runs, and it never causes a 500. The answer is not stored.
- [A18] Test: IdempotencyStoreTest#tombstonedRowIsRejectedNotReplayed; at the API, a keyed /v2 POST whose key row has a NULL response gets 400 text/plain "Invalid request", writes no ledger row and changes no stock.
- [A34] Order on the unversioned POSTs: body validation (@Valid, controller) → Idempotency-Key present (400 for any value, H3) → skuId pattern (service; add 400, purchase 404) → write; the service's unkeyed entry points take no key parameter. Order on the /v2 POSTs: body validation (@Valid, controller) → Idempotency-Key present and well formed (service, 400) → skuId pattern (service; add 400, purchase 404) → claim and write, through IdempotencyStore.run (H2). PUT /v2/inventory/{skuId}/details has no key check: body → skuId → preconditions → write (H7). Each check runs once, in the service or the controller as stated, before any database or idempotency I/O, and neither answer is stored. Each service method names its own answer for a malformed skuId; SkuId depends on no idempotency type.
- [A34] Test: InventoryServiceWriteChecksTest (on /v2 a malformed key, "" included, is 400 before anything else and wins over a malformed skuId; a malformed skuId, with or without a key, touches no repository, transaction or idempotency row); V2WritesApiIntegrationTest (the /v2 order rows: a bad body wins over a bad key, which wins over a bad skuId; neither answer is stored); UnversionedKeyOrderTest and UnversionedIdempotencyIntegrationTest (the unversioned order: a present key, valid or not, is 400 after body validation and before the skuId check, and writes nothing).
- [H1] The four spec operations live at /inventory and match the spec plus OD-5's page cap and the frozen hardening; nothing else. Everything the spec does not list lives under /v2/inventory; /v2 only grows compatibly, and an incompatible change gets /v3. Both versions read and write sku.quantity and the ledger. No unversioned request reads or writes the idempotency table. Test: version-parity walk, no-leak test, ArchUnit rule (L31). "Compatible" means additive response fields and new optional inputs only. A /v2 operation is removed or changed incompatibly only by an owner decision, as a new version; there is no sunset schedule.
- [H2] POST /v2/inventory/{skuId} and POST /v2/inventory/{skuId}/purchase require Idempotency-Key (S3's UUID pattern). Missing or malformed → 400 'Invalid request'. Order: body (@Valid) → key present and well formed → skuId (G11) → claim and write (A34). A key reused for another operation, skuId or request, or older than 24h, is 400 (T1, S8). A repeat with the same request replays the stored status, Content-Type and body (Y4).
- [H3] POST /inventory/{skuId} and POST /inventory/{skuId}/purchase answer 400 'Invalid request' when Idempotency-Key is present with any value (an empty value and a repeated header count), and write nothing and store nothing. Order: body (@Valid) → key present → skuId → write. The unversioned controller and its service methods depend on no idempotency type. Test: HTTP rows for valid, empty, malformed and repeated header; zero rows in sku, ledger and idempotency_keys; ArchUnit rule (L31).
- [H4] GET /inventory returns at most 250 items ordered by skuId (COLLATE 'C'). Only `after` is read: an exclusive cursor compared as a plain string, never validated. `limit` and every other parameter are ignored. When more rows exist the response has Link: <…/inventory?after=…>; rel='next', built from the routed path (C2), carrying only `after`. A query string that can't be decoded, or a repeated `after`, is 400 'Invalid request' (Z3). The deviation is stated in openapi.yaml's info.description and the README.
- [H5] GET /v2/inventory: `limit` non-numeric or below 1 → 250, above 250 → 250; `after` as H4; Link: </v2/inventory?limit=…&after=…>; rel='next'; 400 as Z3. Every list response on either version holds at most 250 items (invariant 7).
- [H6] /v2 routes: GET /v2/inventory, GET /v2/inventory/{skuId}, POST /v2/inventory/{skuId} (add), POST /v2/inventory/{skuId}/purchase, PUT /v2/inventory/{skuId}/details. Every /v2 body is a SkuItem (skuId, quantity, optional details). GET item carries ETag (the details version, "0" before any details) and Cache-Control: no-store; conditional-GET headers are ignored.
- [H7] PUT /v2/inventory/{skuId}/details replaces the whole SkuDetails (field rules: A26). It never changes stock and ignores Idempotency-Key (PUT is idempotent by method). SKU absent: 201 with ETag "1", quantity 0. SKU present: 200 with the new ETag. Without a precondition it is unconditional. 412 (H8) when: If-Match matches no current version; any If-Match, `*` included, on a SKU that does not exist; If-None-Match: * on an SKU that exists. `*` in If-Match means 'a current representation exists' (RFC 9110). An invalid skuId (G11, `;` content included) is 400 'Invalid request'. Order: body (@Valid) → skuId → preconditions → write.
- [H7] A malformed If-Match, and an If-None-Match value other than *, is 400 'Invalid request' (silently ignoring a precondition could overwrite data).
- [H8] G6's four texts plus, on PUT /v2/inventory/{skuId}/details only, 412 with the fixed text above.
- [H10] request_hash = SHA-256 of 'v2' + '\n' + operation + '\n' + skuId + '\n' + canonical request, computed from the parsed request (Y3). A key stored by an unversioned request never matches a /v2 request.
- [H11] The guard filter is driven by route kind (list, item, purchase, details) and applies every frozen check to every route of both versions: ";" in the skuId segment (write item → 400, write purchase → 404, GET → 404, PUT details → 400), Accept refusal on POST and PUT, and the body cap by route kind (4096 bytes for both POSTs on both versions and 65536 bytes for PUT details, each counted while read when the body is chunked; the unversioned chunked exemption of build v2 is lifted, A19, critique M-01), all on the routed path. Tie-break for equally specific Accept ranges stays "first listed" (C3). Test: a route-enumeration test lists every mapped route with {skuId} and asserts the frozen answer plus zero rows written; a new route the filter does not know fails it.
- [H16] Because the guard filter runs before argument resolution, a request that has both a ";" skuId and a bad body gets the skuId answer (400 for add and PUT details, 404 for GET and purchase), not the body's 400. U3 and G4's "a bad body wins" hold everywhere the filter does not decide. (M-13)
- [A17] The Idempotency-Key is a UUID wherever it is read (S3); OpenAPI says format uuid; no replay header.
- [A19] A write body over its cap is 400 'Invalid request' before it is parsed: 4096 bytes for both POSTs on both versions and 65536 bytes for PUT /v2/inventory/{skuId}/details. - [H17] spring.datasource.hikari.connection-timeout is 3000 ms and every connection sets Postgres lock_timeout to 5 s (connection init SQL SET lock_timeout = 5000), so a request waiting on a locked row answers 500 "Internal server error" (G6) after about 5 s, a request starved of a pooled connection after about 3 s, and at worst, when both waits happen, after up to about 10 s, instead of holding for the 30 s default and starving the 10-connection pool (critique M-14). A lock timeout is a server fault, so the 500 stays within G10. The init SQL also applies to the Flyway connection: a migration that waits more than 5 s for a lock fails startup (accepted). A test that holds a row lock in a second connection asserts the 500.

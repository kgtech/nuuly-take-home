# Critique — intv (Interview defense) — v2 @ d01852a (reviewer report)

## Findings
- F-intv-01 MAJOR — The Redis idempotency fast path (`ReplayCache`, `replay-put.lua`, interceptor lines 63-75; DESIGN §1 row, §2 step 2, §5 alt. 3) has no recorded reason or benefit: the Postgres claim is one indexed INSERT needed anyway; replays are rare; the copy adds a Lua script, a two-clock age check, a cache-served 400 path, a second after-commit hook and fault tests. The first build rejected "Redis in front" (DECISIONS.md:841, Z1 option D); V2 reverses it without saying why. The alternative "Postgres-only idempotency, Redis only for hot reads" is absent from §5. Question: "What does idem:{key} buy you? How many replays/s were you designing for?" Fix: remove ReplayCache, or record the reason, the rejected alternative and the tradeoff.
- F-intv-02 MAJOR — "Most used is what LFU keeps" (DESIGN:49, README:110) is contradicted by the mechanics: a stock entry lives one TTL (5 s) from its populate; a hit does not renew it and a refresh keeps the remaining TTL, so every SKU is evicted every 5 s and repopulated on the next miss with a fresh LFU counter. Membership is "read in the last 5 s", not frequency; LFU only matters if the set read within 5 s exceeds 64 MB, and the memory pressure comes from the 24 h idem: entries sharing the policy. Also "stays while it keeps being read" (§3) is not what happens. Fix: state honestly that the hot set is "SKUs read within the last TTL" and that LFU is a backstop shared with the replay copies; record in DESIGN/A6.
- F-intv-03 MINOR — §4 understates the Redis-slow cost of a keyed POST: lookup + stock refresh + replay put are three synchronous calls → up to 750 ms, not 500. Repro: pause Redis, time a keyed POST on a SKU read before the pause.
- F-intv-04 MINOR — 5 s TTL, 250 ms timeout, 64 MB maxmemory have no reason on record (why these values, what traded).
- F-intv-05 MINOR — READ COMMITTED correctness argument incomplete on record: the guarantee is Postgres re-evaluating `WHERE quantity >= :q` against the new row version after the lock wait (PostgreSQL docs §13.2.1), not just "serializes writers"; lock order (idempotency row, sku row, KEY SHARE for the ledger FK) and the concurrent-new-SKU insert case are unmentioned. Question: "Two purchases of 5 against stock 5 both read 5 before either commits. Why doesn't the second succeed?"
- F-intv-06 MINOR — The DB-enforced alternative for balance = ledger (a BEFORE INSERT trigger on inventory_ledger applying the delta to sku.quantity) is neither chosen nor listed as rejected, although §6 admits the weakness and the build already trusts triggers.
- F-intv-07 MINOR — UUID-only Idempotency-Key (S3): rejected options recorded, positive reason missing; Stripe/IETF accept any opaque string ≤ 255. Record gap, not code gap.
- F-intv-08 MINOR — 28 decisions in DECISIONS.md carry "_No notes recorded._" (G7, G12, G13, G14, D6–D9, R1, R3, R4, R6, R8, R9, S5–S12, T2, T6, U3, W1, W2, X1); several are exactly the interview questions (G7, G14, R4, R9, S8, U3). DECISIONS.md is read-only in V2; the answers need recording elsewhere (DECISIONS-ADDED / interview-defense).
- F-intv-09 MINOR — FE9 drops the key on 5xx; the reason it is safe (a 500 here implies the claim and stock change rolled back together; the after-commit hooks are guarded) is not on record; Stripe's guidance is to reuse the key on 5xx/timeouts. Question: "What if the 500 happened after the commit?" (See also F-fe-01: with a proxy 502 it is not safe.)
- F-intv-10 MINOR — Z1's justification for the AOP idempotency advice (retry wrapping idempotency) evaporated in V2; A10 records the shape was kept, not why it is still worth an interceptor + pointcut + generic result-adapter registry + REQUIRES_NEW (no outer transaction exists) versus a direct call.
- F-intv-11 NIT — DESIGN:19 writes `INSERT INTO sku (sku_id, quantity, version) VALUES (:id, 0, 0)`; code inserts sku_id only (defaults). DESIGN:49 "stays while it keeps being read" (see F-intv-02). compose.override.yaml makes Redis a hard startup dependency (depends_on service_healthy) while README says Redis can be stopped any time; whether the app starts with Redis absent is neither tested nor stated.
- F-intv-12 NIT — Two clocks decide the 24 h expiry (DB now() vs app clock on the Redis created field); skew s lets Redis replay/reject for s seconds around the boundary. Harmless at this scope; say so.

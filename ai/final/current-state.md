# Current state of the `final` tip (build v2 code) against the final target

Study for the plan gate. Three read-only reviewers read the code, the tests, `CLAUDE.md`/`DECISIONS.md` (#87's exports) and build v2's records; their reports are merged below without rewriting (each marks what it did not run as UNVERIFIED). The unverified claims are collected in `ai/final/board-cards.md` and become the first tests of Part 2.

## Headlines
1. **The code is build v2's, not #87's plan.** Stock is a `sku.quantity` balance row updated by a conditional UPDATE at READ COMMITTED, plus an append-only ledger. Idempotency is one explicit call, `IdempotencyStore.run`. There is no advisor, no `@Retryable`, no JPA. So G7/W1/W2/X1/Y2 in `CLAUDE.md` describe a design the code does not have; the cards E1-E3, A37-A39, Z2, D5, D10, S4 and S11 also name things the code lacks (Part B).
2. **A real defect, read from the code (not yet reproduced):** the guard filter skips `/v2/.../purchase` (`!routed.v2()`, `InventoryRequestGuardFilter` line 68) and any 3-segment `PUT`. With the target routes, a `;` in the skuId would reach a keyed write on another SKU (lesson L21). The fix is to drive the filter by route kind, not by version or segment count.
3. **Today's `/v2` is create-with-details (201/409) and `PUT /v2/inventory/{skuId}`.** OD-6 removes both and adds `/v2` add, purchase and `PUT .../details`. About 15 tests go away, and every keyed test moves from the unversioned paths to `/v2`.
4. **Invariants 4, 5 and 6 have no real test today**; 3 runs in only 5 classes; 1, 2 and 7 are covered on the unversioned paths only.
5. **The idempotency CHECKs allow `'create'` and 201/409 (V3).** Narrowing them with a plain `ADD CONSTRAINT` fails on any database that holds such a row. See the V4 card.
6. **No ArchUnit, no `.github/workflows/`, no `openapi-v2.yaml`, no conformance test** on the tip.

### 1.3 Guard filter (`web/InventoryRequestGuardFilter.java`)

What it does today (routing, :99-115; check, :61-93):
- `routed()` strips a leading `v2` segment, then requires first segment `inventory` and `segments.size() >= 2` after that, i.e. `/v2/inventory` (list) is skipped, `/v2/inventory/x` is size 2.
- `single = segments.size()==2`; `purchase = !routed.v2() && size==3 && third=="purchase"` (:69-70) so /v2 purchase is skipped (there is no such route today).
- `write = POST || (v2 && PUT)` (:66-67). Check block runs only if `size>=2 && (get&&single || write&&(single||purchase))` (:71). So `PUT /v2/inventory/{skuId}/details` (3 segments, not purchase) is NOT checked at all: no `;` check, no Accept check, no body cap (only `Content-Length` cap and `CappedBodyRequest` :86-90 are in the block).
- `;` check :73-76: error is 400 when `write && single` else 404.
- Accept check `write && !acceptsJson` -> 400 :77-80. Body cap :81-85 (4096 unversioned, 65,536 v2). Chunked cap (`CappedBodyRequest`) only for `write && v2` :86-90; unversioned chunked bodies are NOT capped today (only Content-Length is compared), unverified whether Tomcat/Jackson bounds it elsewhere (A19 says the cap; the chunked unversioned gap is an existing divergence worth a test).
What must change so every rule applies to every /v2 route:
1. Classify by route kind, not by "v2 or not": `kind = LIST | ITEM | PURCHASE | DETAILS` derived from (segments after `inventory`): 1 = LIST, 2 = ITEM, 3+`purchase` = PURCHASE, 3+`details` = DETAILS (for both versions, where the version only decides which kinds exist). Then `;` on the sku segment: ITEM POST -> 400, ITEM GET -> 404, PURCHASE POST -> 404, DETAILS PUT -> 400 (Target: "invalid skuId answers 400 on POST /v2/inventory/{skuId} and PUT details, 404 on GET and purchase").
2. Remove `!routed.v2()` from `purchase` (:69).
3. Extend `write` to include PUT on DETAILS (today `routed.v2() && PUT` only matters for the two-segment path).
4. Body cap by route kind: 4096 for add/purchase (both versions), 65,536 for DETAILS; apply `CappedBodyRequest` to every write route (drop the `routed.v2()` condition at :86) so unversioned chunked bodies are capped too. That is a behavior change on the unversioned path that hardens toward the spec's hardening list (A19), not a new kind of check; log it.
5. Matrix segments on literal segments (`/v2;x/inventory/...`, `.../purchase;x`, `.../details;x`) are ignored via `valueToMatch()` already (:70, :107, :111).
6. `PUT` on an unversioned path stays unrouted (405 by Spring). `single`-only checks for other methods (DELETE etc.) keep the standard 405/404.
Tests: `T/inventory/RequestGuardTomcatIntegrationTest` (parameterized `requests()` :44-64: v2 rows `POST /v2/inventory/ABC-1%3Blot=7` etc. use the old create body `V2_BODY`; `PUT /v2/inventory/...` rows move to `/details`; ADD rows for `POST /v2/inventory/ABC-1;x/purchase` -> 404, `POST /v2/inventory;v=1/...`, `PUT /v2/inventory/ABC-1;lot=7/details` -> 400, and each Accept q=0 / xml row for v2 add, v2 purchase, details; `chunkedV2BodyIsCappedWhileRead` :88 retarget to PUT details and add chunked unversioned + chunked v2 add). `T/inventory/InventoryRequestGuardIntegrationTest.matrixSegments()` (:59-64) and `postWhoseAcceptExcludesJsonIs400AndWritesNothing` (:79) parameterize over version: run the same matrix against `/inventory` and `/v2/inventory` (the version-parity guard test). `SkuDetailsApiIntegrationTest.guardCoversV2Paths` :562 is replaced by that shared matrix.

## 3. Idempotency: current state and V4

Handling today: explicit call in service (no AOP): `InventoryService.write` :105-122 — order: key absent -> plain tx (`transaction.execute`) after `SkuId.isValid`; key present -> `IdempotencyKey.parse` (UUID regex, `M/idempotency/IdempotencyKey.java`) -> `SkuId.isValid` -> `IdempotencyStore.run(key, operation, skuId, canonicalRequest, write)` (`IdempotencyStore.java:75-99`): opens/joins a READ COMMITTED tx, `INSERT ... ON CONFLICT (idempotency_key) DO NOTHING RETURNING` (CLAIM :39-44); no row -> `replay` (`STORED` :47-52, 24h via DB clock `KEY_VALIDITY` :48-49; different operation/skuId/hash, expired, or `status IS NULL` -> `Keyed.Invalid` -> 400); row -> write then `COMPLETE` UPDATE (:55-59). Response rendering shared via `OutcomeResponses.toStored` (`web/OutcomeResponses.java:38-51`) through `KeyedResponses`.

Request hash: `RequestHash.of(operation, skuId, canonicalRequest)` = SHA-256 of `operation.dbValue()+"\n"+skuId+"\n"+canonicalRequest` (`RequestHash.java:16-23`); canonical for add/purchase is the quantity as decimal digits (`InventoryService.java:58,67`); for create it was `CreateSku.fingerprint`. No API version in the hash.

Schema (V2 and V3, exact):
- V2 `idempotency_keys`: `idempotency_key uuid PK`; `operation text NOT NULL CHECK (operation IN ('add','purchase'))` (auto-named `idempotency_keys_operation_check`); `sku_id varchar(64) COLLATE "C" NOT NULL` (no FK); `request_hash bytea NOT NULL CHECK (octet_length = 32)`; `status smallint CHECK (status IN (200,400,404))` (`idempotency_keys_status_check`); `content_type text`, `body text`, `created_at timestamptz NOT NULL DEFAULT now()`; `idempotency_response_complete CHECK ((status,content_type,body) all NULL OR all NOT NULL)`.
- V3 (`V3__sku_details.sql:20-28`) drops and re-adds both checks: operation `IN ('add','purchase','create')`, status `IN (200,201,400,404,409)`.
So exactly what is allowed now: operations add/purchase/create; statuses 200/201/400/404/409.

Is narrowing safe? A `create` operation and 201/409 statuses exist in stored rows only if someone called the build-v2 keyed `POST /v2/inventory/{skuId}` (keyed create). Rows are never purged (R9), so `ALTER TABLE ... ADD CONSTRAINT ... CHECK (...)` fails on a database that holds any such row. Facts:
- Postgres `ADD CONSTRAINT ... NOT VALID` enforces the new CHECK for future inserts/updates without scanning existing rows, so V4 cannot fail on existing data. Trade-off: constraint stays "not validated" (`convalidated=false`) until a later `VALIDATE CONSTRAINT`. (Postgres behavior known; not run here.)
- No code reads a stored 'create' row except the replay branch, which compares `operation` strings only (`IdempotencyStore.replay` :107-109), so leftover rows are harmless: a leftover `create` key on /v2 add fails as different operation -> 400.
- Tests that assert the wide CHECKs: `T/inventory/SkuDetailsSchemaTest.acceptsTheBoundaryValuesAndTheCreateKeyStatuses` :74-86 (inserts 'create' with 201/409) -> must be rewritten as "rejects create/201/409" if narrowed; `T/idempotency/IdempotencySchemaTest` (checks status/operation rows; grep before editing) and `T/inventory/SkuDetailsSchemaTest`.
V4 options for the owner:
1. Narrow with NOT VALID (recommended if you want the schema to say what the API can store; safe on any DB; cost: unvalidated constraint on legacy rows, and a `VALIDATE` step in a later migration if wanted).
2. Leave V3 CHECKs as they are and remove only the Java `Operation.CREATE` (no DDL; zero risk; leaves dead permitted values, the schema then lies about what is stored).
3. Narrow with validation (fails if any legacy row exists; only safe if a check confirms none; don't).
Hash/version: recommended to add the API version to the hash input (e.g. `"v2\n"` prefix or a `version` argument to `RequestHash.of`), so a key stored by build v2's unversioned POST (same inputs, `InventoryItem` body) never replays on /v2 and gets 400. No DDL needed. Alternative: distinct `operation` values (`add`/`purchase` are shared with ledger `reason`, `Operation.java:4-5` comments the vocabulary link, so changing them breaks that symmetry and needs the CHECK to change). Tests to update: `RequestHashTest` (`hashIsSha256OfOperationSkuIdQuantity` :21, `eachFieldChangesHash` :29, `hashIs32Bytes` :50) - the first would change bytes; note `RequestHash` javadoc :8-9 promises the bytes stay as they were (A33), so a card must change.
